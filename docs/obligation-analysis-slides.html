Policy Obligation Analysis

Catching fact-database runtime exceptions at compile time

What is it?

  • It's a new check in the policy compiler for fact mutations that can fail at runtime.
  • It checks every create, update and delete, including those inside finish functions.
  • It also catches the same fact being changed twice in one finish block.
  • It's opt-in with --check-obligations, and it only produces warnings.

What is the status?

Working

  • All five fact-mutation invariants are checked on every path.
  • Mutations inside finish functions are checked at each call.
  • Init commands are understood to start with no facts.
  • if and match, as statements or expressions, and helper functions provide proof.
  • Keys read from query results provide proof for the fact they came from.

Not yet

  • Creating two facts of one name with different literal keys in an init command still warns.
  • The runtime still lets some of these errors through silently.
  • There's no PR yet.

Obligations

Every fact mutation has a precondition that must hold when it runs. We call that precondition its obligation.

MutationObligationAfterwards
create F[k]F[k] must not existF[k] exists
update F[k]F[k] must existF[k] exists
update F[k]=>{v: x}The stored v must equal xF[k] exists
delete F[k]F[k] must existF[k] does not exist
Any mutationOnly once per fact in a finish block
finish {
    create Account[user: this.user]=>{balance: 0}
    // obligation: Account[user: this.user] must not exist
}

If an obligation doesn't hold, the command fails with a runtime exception.

Observations

An observation is something a path has learned about the fact database.

A check ends the command when it fails. So the code after it knows the check passed.

check !exists Account[user: this.user]
    else recall already_open()
// observed: Account[user: this.user]
//           does not exist
finish {
    create Account[user: this.user]=>{..}
    // obligation met
}

Every path needs proof

The analysis follows each path separately. An obligation is only met if an observation on that same path proves it.

if this.user == 1 {
    check !exists Account[user: this.user]
        else recall already_open()
}
finish {
    create Account[user: this.user]=>{..}
}

Here only one of the two paths checks first, so the compiler warns.

Mutations are observations too. After a create, the path knows the fact exists, so a second create of it is caught.

How does it work?

What counts as proof

StatementProves
check !exists F[k] else ...F[k] absent
check exists F[k] else ...F[k] exists
let x = query F[k] or ...F[k] exists
if / match on theseEach branch its side
A helper function callWhat the helper proves
attributes { init: true }No facts exist

How keys are matched

A let alias still matches the original expression.

let uid = this.user
check !exists Account[user: uid] else ...
create Account[user: this.user]=>{..}  // proven

A ? in a check covers every value of that key.

check !exists Grant[user: u, perm: ?] else ...
create Grant[user: u, perm: 3]=>{}  // proven

Complex checks are pointed out

A check like !(exists F[k] && ok) proves nothing, but the warning points at it so the author knows what to simplify.

Following finish functions

A call to a finish function is followed into its body. Its parameters are replaced by the caller's arguments, so a check in the command proves a mutation inside the function.

finish function open_account(u int) {
    create Account[user: u]=>{balance: 0}  // proven by the caller's check
}

command Open with Base {
    policy {
        check !exists Account[user: this.user] else recall already_open()
        finish {
            open_account(this.user)
        }
    }
    ...
}

A warning inside a function points back to each call that reached it.

Example: the bug

The SetCounter command in the core example policy creates a counter without checking for it first.

policy {
    finish {
        create Counter[name: this.name]=>{value: this.value}
        emit CounterSet{name: this.name, value: this.value}
    }
}

Running it twice with the same name creates a fact that already exists.

warning: cannot prove `Counter[name: this.name]` does not exist before `create`
    |
179 |   create Counter[name: this.name]=>{value: this.value}
    |   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ this fact may already exist
    |
    = note: creating a fact that already exists is a runtime exception
    = help: check that it does not exist first: `check !exists Counter[name: this.name] else ...`

Example: the fix

Adding the check the warning suggests, with a recall block to handle the failure, fixes it.

command SetCounter with Base {
    ...
    policy {
        check !exists Counter[name: this.name] else recall reject()
        finish {
            create Counter[name: this.name]=>{value: this.value}
            emit CounterSet{name: this.name, value: this.value}
        }
    }

    recall reject() {}
}

With this change, the policy compiles with no warnings.
